# Rider-Pi 1.0.0

This release establishes a common Rider-Pi software baseline after quality,
security and device-operation fixes. It introduces project version `1.0.0`,
tag `v1.0.0`, English/Polish READMEs and visible signals from existing checks.

## Included changes

- Shared motion gate, one UART owner, command identity/freshness validation,
  explicit operator consent and acknowledgments distinct from physical completion.
- Operator panel, calibration profiles, service/resource diagnostics and Git
  revision footer, without automatic arming when a page opens.
- HTTP, file, process and private-data boundary protections, plus reliability
  and maintenance fixes from the Sonar finding review.
- Isolated Python 3.9 and JavaScript tests, both measured coverage reports
  imported in CI, and a Sonar gate for exact PR and `main` revisions.
- LCD startup independent of API readiness, safe root/pi lock handover,
  driver import after acquiring the lease and transfer to the status renderer.
  Installed 270° compensation and idle sleep are preserved.
- Optional compute and bounded navigation decisions through the paired Venom
  module; hardware execution and validation remain on Pi.

## Compatibility and upgrade

The device baseline remains the manufacturer's Debian 11/Bullseye image with
Python 3.9. This release does not change SDK, firmware, pins or API contract
versions. Private configuration stays outside Git; preserve it rather than
replacing it with templates. Google SDKs and ML models remain profile-specific
optional dependencies.

For application updates, follow [deployment](../DEPLOYMENT.md) using the full
integration SHA. Unit, driver, boot or runtime changes require their own scope
and validation; a tag alone does not authorize installation of those components.
This release increment changes documentation and metadata and needs no service restart.

## Reading quality results

[README badges](../../README.md) show live analyses and can change after release.
The [quality guide](../QUALITY_GATE.md) explains gate conditions, coverage and PR
checks. Individually reviewed Accepted/False positive dispositions are separate
from source fixes.

Autonomy, perception, mapping and odometry remain experimental. Software tests
and accepted LCD frame writes do not establish physical safety or perception
quality in every scene. Movement requires a separate plan and operator consent;
publishing a release does not arm the robot.
