# Rider-Pi 1.0.0

Wydanie porządkuje wspólną bazę oprogramowania Rider-Pi po naprawach jakości,
bezpieczeństwa i obsługi urządzenia. Wprowadza numer projektu `1.0.0`,
tag `v1.0.0`, README PL/EN i widoczne wskaźniki istniejących kontroli.

## Zakres wydania

- Wspólna brama ruchu, jeden właściciel UART, walidacja tożsamości i ważności
  poleceń, jawne zgody operatora oraz rozdzielenie ACK od fizycznego wykonania.
- Panel operatora, profile kalibracji, diagnostyka usług/zasobów i rewizja Git
  w stopce, bez automatycznego uzbrajania po otwarciu strony.
- Ochrona granic HTTP, plików, procesów i prywatnych danych; poprawki niezawodności
  oraz utrzymania wynikające z przeglądu zgłoszeń Sonara.
- Izolowane testy Python 3.9 i JavaScript, import obu raportów coverage w CI
  oraz bramka Sonara dla dokładnych SHA PR i `main`.
- Poprawiony start LCD bez zależności od gotowego API, bezpieczna blokada
  współdzielona root/pi, import sterownika po uzyskaniu blokady i przekazanie
  LCD do renderera statusu. Zachowana kompensacja montażu 270° i wygaszenie.
- Opcjonalne obliczenia i ograniczone decyzje nawigacyjne przez sparowany
  moduł Venoma; wykonanie sprzętowe i walidacja pozostają na Pi.

## Zgodność i aktualizacja

Baza urządzenia pozostaje na obrazie producenta Debian 11/Bullseye i Pythonie
3.9. Wydanie nie zmienia SDK, firmware, pinów ani wersji kontraktów API.
Konfiguracja prywatna pozostaje poza Git; nie nadpisuj jej szablonami.
SDK Google i modele ML są opcjonalne, zależnie od wybranego profilu.

Dla aktualizacji aplikacji stosuj [procedurę wdrożenia](../WDROZENIE.md)
z pełnym SHA integracji. Zmiany unitów, sterowników, rozruchu lub runtime
wymagają osobnego zakresu i sprawdzenia; sam tag nie upoważnia do ich instalacji.
Ten przyrost wydania zmienia dokumentację i metadane; nie wymaga restartu usług.

## Interpretacja jakości

[Odznaki README](../../README_PL.md) pokazują wyniki bieżących analiz, więc mogą
zmienić się po wydaniu. Bramkę, zakres pokrycia i kontrole PR opisuje
[bramka jakości](../BRAMKA_JAKOSCI.md). Indywidualne oceny Accepted/False positive
nie są naprawami kodu i pozostają odrębne od poprawek źródłowych.

Autonomia, percepcja, mapy i odometria zachowują charakter eksperymentalny.
Testy programowe i przyjęcie zapisu obrazu przez LCD nie stanowią odbioru
fizycznego bezpieczeństwa ani jakości percepcji w każdej scenie. Ruch wymaga
osobnego planu oraz zgody operatora; wydanie nie uzbraja robota.
